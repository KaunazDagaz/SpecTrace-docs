## 1. Рабочий сценарий

На принятой версии одна команда берёт RFC 6902 и выдаёт реестр проверенных требований, предложенные для них тест-кейсы и матрицу трассировки с видимыми пробелами.

Конвейер схлопывает пробельные символы документа, сохраняя карту обратно в исходный файл, и строит индекс его разделов. Он отправляет весь документ одним запросом в `gemini-3.5-flash-lite` и просит кандидатов в требования в виде текста цитаты, модальности и тестируемости — но никогда не позиций. Затем код находит каждую цитату точным совпадением. Цитата, которая не найдена, попадает в `rejected-quotes.json`. Цитата, найденная больше одного раза или заявленная с противоречащими прочтениями, попадает в очередь решений для человека. Каждая остальная цитата становится требованием с идентификатором из хэша содержимого, диапазоном символов и номером раздела.

Для каждого требования, которое модель классифицировала как тестируемое, второй вызов отправляет только номер раздела и цитату и получает до трёх тест-кейсов. Идентификатор требования прикрепляет код, а не модель. Матрица выводится только из реестра и кейсов: каждое требование либо покрыто, либо является пробелом, а кейсы, ссылающиеся на отсутствующее требование, перечисляются как осиротевшие. `matrix.html` сообщает вверху, что покрытие считается по предложенным, непроверенным кейсам и что она не утверждает, будто спецификация покрыта полностью.

Каждый вызов модели проходит через дисковый кэш с ключом из хэша полного запроса. С `--offline` весь прогон воспроизводится из `cache/` без ключа и без сети, а промах кэша — это ошибка.

Команда, которая это демонстрирует, из корня репозитория. Сегодня она была запущена на `a976ace` и завершилась с кодом 0:

```
dotnet run --project src/SpecTrace.Cli -- run --document corpus/rfc6902.txt --offline
```

Она записывает семь файлов в `runs/rfc6902-3ff2234db6aa/`; матрица — это `matrix.html` там же. Сегодня шесть файлов, кроме `manifest.json`, побайтно совпали с `runs/reference/`.

## 3. Эталонный прогон в цифрах

Источник: `runs/reference/` на `a976ace`; подсчитано по файлам сегодня и сверено со сводкой CLI сегодняшнего воспроизведения. Идентификатор прогона `rfc6902-3ff2234db6aa`, модель `gemini-3.5-flash-lite`, температура 0.

**Эти числа описывают один прогон по одному документу. Качество относительно эталонной разметки измеряется в M2, и ни одно число здесь не является утверждением о качестве.** В частности, 12 — это сколько требований вернула модель и проверил код. `export` тоже упоминается в справке CLI. Он не реализован, и ни одна задача его не содержит.

### Что это значит для результатов M1

- **Решений человека нет нигде.** Все 23 кейса — `proposed`. «Покрыто» означает, что модель предложила кейс, который ещё не прочитал ни один человек. Статусы «нетестируемо» и «отложено» ни разу не появлялись в настоящем прогоне; они есть только в модульных тестах.
- **В реестре нет четырёх настоящих требований.** "The target location MUST exist for the operation to be successful." встречается в §4.2 и §4.3, а "The "from" location MUST exist for the operation to be successful." — в §4.4 и §4.5. Без контекста ни одно из них нельзя свести к одному диапазону, поэтому оба ждут в очереди решений (N3 §4).
- **Одно предложение несёт два обязательства.** В предложении из §5 есть `SHOULD` и `SHALL NOT`. Модель вернула его дважды с разными модальностями, поэтому оно ушло в очередь с обоими прочтениями, и ни одного из прочтений нет в реестре (PR [#6][pr6]).
- **Единственный пробел порождён извлечением.** Это вводная фраза списка, процитированная без самого списка (N4 §2).
- **Модель классифицировала все 18 утверждений как `testable`.** Пути `needs_human_decision` и `not_testable` проверяются только тестовыми фикстурами.
- **Загрязнение.** RFC 6902 широко известен и почти наверняка есть в обучающих данных модели (§14 плана).

### Не проверено или проверено лишь частично

- Десять проверок разделов (2.5) и наблюдение человека за настоящим прогоном (M.2) подтверждает студент.
- NFR-07 — полный живой прогон в пределах бесплатного тарифа без ручного вмешательства — повторно не запускался, потому что он тратит дневную квоту. Записанная живая генерация заняла 6,5 минуты на 12 вызовов при примерно 1,5 минуты чистого ограничения частоты. Повторные попытки не журналируются, поэтому причина — догадка (N4 §5). На `gemini-3.5-flash` бесплатный тариф давал 20 запросов в день, "less than one full run" (PR [#5][pr5]).
- Живой путь Gemini сегодня не проверялся: `LiveGeminiTests` пропущен, потому что ключ не был задан. Самый новый записанный живой ответ — от 23 сентября 2026 г.
- NFR-04, "swappable via configuration": поставщик `gemini` и модель `gemini-3.5-flash-lite` — константы в [`LlmClientFactory`][factory]. Замена — это изменение кода, а не конфигурации, и существует только одна реализация поставщика. Обещание P4, что замена меняет качество, но не корректность, со вторым поставщиком не проверялось.
- Определение исчерпанной дневной квоты считает исчерпанной квоту, чей `quotaId` содержит "PerDay". Значения этого поля не задокументированы (PR [#5][pr5]).
- Схема генерации не отправляет `maxItems`. Парсер обеспечивает "at most 3 cases" и проваливает прогон, если кейсов больше (N4 §3).
- Шаг CI "Reproduce" доказывает, что команда из README выполняется на обеих платформах. Побайтное сравнение выполняется раньше — `OfflineEndToEndTests` в шаге "Test", а не шагом "Reproduce".
- `git_sha` в `manifest.json` берётся из сборки. Сборка без `.git` записывает `unknown`, а грязное рабочее дерево не отмечается (N5 §3).
- `extract` не записывает манифест (N5 §4).
- Одна из 14 закоммиченных записей кэша, извлечение `gemini-3.5-flash` `246ce833…`, не используется эталонным прогоном (N5 §5).
- `LiveGeminiTests` тратит настоящий запрос всякий раз, когда задан `GEMINI_API_KEY` (N4 §4, N5 §6).
- Два пункта §12 TOR всё ещё открыты: политика поставщика по использованию данных на бесплатном тарифе и условия распространения RFC 6902.
- Проверены только Windows и Linux.

Для каждого вопроса сначала приведены факты со ссылками на доказательства, затем выводы. **Выводы подготовлены агентом в черновике на проверку студенту.** Каждый вывод опирается на факты, перечисленные над ним. На их основании ничего не менялось.

### 8.1 Что сработало

Факты:

- Все 16 запусков CI в `spectrace-dev`, с [1][run1] по [16][run16], завершились успешно — на каждом PR и на каждом коммите слияния. Три проверки, повторённые сегодня, проходят.
- Эталонный прогон воспроизводится побайтно на Linux и Windows. Сегодня он воспроизвёл 13 из 13 вызовов модели из кэша без ключа.
- Ни одна выдуманная цитата не попала в реестр: в эталонном прогоне верификацию провалили 0 из 18 утверждений, а фикстура с выдуманной цитатой отклоняется (`AFabricatedQuoteIsDroppedFromTheRegisterAndRecordedVerbatimAsRejected`).
- Проверка на настоящем корпусе и настоящем API нашла три ошибки в плане до того, как они попали в продукт: регулярное выражение разделов (PR [#2][pr2]), отсутствующий заголовок `Retry-After` (N3 §3) и неподтверждённое ключевое слово `maxItems` (N4 §3).
- Противоречие между REQ-MTX-02 из TOR 1.0 и статусами в плане выявилось во время SPEC-4 и было разрешено поправкой к TOR, а не только в коде (`a772f38`, PR [#7][pr7]).
- 16 идей и наблюдений попали в заметки, а не прервали задачу: 5 в N3, 5 в N4, 6 в N5.
- Набор тестов вырос со 138 пройденных на SPEC-3 (PR [#4][pr4]) до 251 сегодня.

Выводы (черновик агента, на проверку студенту):

- Для M1 центральная ставка проекта оправдалась: верификация и кэш делают результат проверяемым и воспроизводимым без доверия ни к модели, ни к ключу.
- Правило "Verify, don't assume" окупилось. Каждая из трёх ошибок плана была бы незаметной: неверные метки разделов, повторы, игнорирующие подсказку поставщика, ключевое слово схемы, которое может игнорироваться.

### 8.2 Какое допущение оказалось неверным

Факты:

- Blueprint §8 выбрал Gemini Flash за "Zero marginal cost at this scale". Бесплатный тариф 3.5 Flash давал 20 запросов в день, меньше одного полного прогона (PR [#5][pr5]). В период 20–23 сентября квота оставалась исчерпанной дольше, чем говорила любая подсказка о повторе (N3 §3).
- Регулярное выражение из §5.5 плана пометило бы 389 из 1011 строк как "9.2" (PR [#2][pr2]).
- REQ-MTX-02 из TOR 1.0 не могло выполняться одновременно со статусами `NotTestable` и `DeferredByHuman` из плана (`a772f38`).
- Контракты из §6 плана, названные замороженными, потребовали нового поля `PromptSha256` и более богатой записи очереди (N3 §2; PR [#6][pr6]).
- План считал цитату, найденную дважды, крайним случаем, для которого нужно "count how often it happens" (§14). В настоящем прогоне это касается 2 из 15 разных предложений и 4 настоящих требований (N3 §4).
- План ожидал M1 к 20 сентября. Она завершилась 25 сентября.

Выводы (черновик агента, на проверку студенту):

- Не подтвердились допущения о внешних фактах: квотах поставщика, вёрстке RFC и о том, как часто текст повторяет сам себя. Архитектура выдержала. Квоте нужен собственный бюджет в плане M2, потому что базовая ветвь эксперимента и любая вторая модель будут тратить её каждая (N3 §3).
- Слово "frozen" в §7 TOR обещает больше, чем план смог выдержать. Либо контракты получают версию и историю изменений, как TOR, либо TOR перестаёт называть их замороженными.

### 8.3 Где потеряно время

Факты:

- SPEC-2 слит 20 сентября в 17:40 UTC. PR SPEC-3 открыт 23 сентября в 07:07 UTC. N3 §3 фиксирует, что квота Flash была исчерпана в период 20–23 сентября.
- Работа, сделанная дважды:
  - комментарии агента удалены после SPEC-3 (вторая часть [`417fa38`][c-417fa38]), затем ещё раз из файлов SPEC-1 и SPEC-2 (PR [#4][pr4]);
  - извлечение перезаписано на новой модели (PR [#5][pr5]);
  - верификатор и доля верификации исправлены после слияния (PR [#6][pr6]);
  - эталонный прогон перегенерирован, потому что его манифест называл более ранний коммит ([`f0556b7`][c-f0556b7]).
- 12 живых вызовов генерации заняли 6,5 минуты при примерно 1,5 минуты ограничения частоты (N4 §5).
- Часы по задачам нигде не записаны там, где агент может их прочитать.

Выводы (черновик агента, на проверку студенту):

- Самой большой единичной потерей было ожидание квоты бесплатного тарифа между SPEC-2 и SPEC-3, и квота была потрачена на модель, которую потом заменили. Проверка дневного лимита до выбора модели — пункт VERIFY в §12 TOR — сэкономила бы это время.
- Большая часть переделок — это вывод агента, не соблюдавший либо уже существующее правило (без комментариев), либо определение, уже записанное в плане (§8.5). И то и другое дешевле поймать до PR, чем после слияния.

Заполняет студент — часы по задачам, если они учитывались:

### 8.4 Какие дефекты повторялись

Факты:

- **Концы строк на Windows** — в четырёх задачах: корпус (SPEC-2, [`476c705`][c-476c705]), файлы промптов (SPEC-3, [`417fa38`][c-417fa38]), JSON-артефакты (SPEC-4, [`da0936e`][c-da0936e]) и запись кэша, которая писала CRLF (SPEC-5, [`9e37019`][c-9e37019]).
- **Комментарии, написанные агентом**, удалялись дважды ([`417fa38`][c-417fa38], PR [#4][pr4]), прежде чем правило их запретило.
- **Записи PR**:
  - у PR [#1][pr1] и [#8][pr8] нет описания;
  - ни один из восьми PR не перечисляет свои критерии приёмки по одному с указанием, как проверен каждый, хотя этого требует `CLAUDE.md`;
  - ни у одного PR нет ревью или комментария человека; единственные ревью — два комментария Copilot о том, что он не смог провести ревью из-за лимита квоты;
  - шесть из восьми PR слиты через 61–126 секунд после открытия; PR #5 — через 1 час 40 минут, PR #6 — через 5 минут 25 секунд.
- **Нумерация**: PR [#1][pr1] называется "SPEC-5-projec setup", PR [#3][pr3] — "SPEC-7: …" поверх коммита с заголовком "SPEC-3: …", а PR [#8][pr8] — "Spec 9 offline reproduction" (N5 §2).
- **Документация написана, но не опубликована**: N3 и N4 не отслеживаются; N5 и поправка TOR 1.1 лежат в неотправленных ветках; до этого PR в `SpecTrace-docs` не было ни одного PR.
- **Неверные пути в документах**: TOR ссылается на `research/decisions.md`, которого не существует (N3 §1), а `CLAUDE.md` ссылается на имена файлов в нижнем регистре (N5 §1).
- **Живой тест тратит квоту** (N4 §4, N5 §6).

Выводы (черновик агента, на проверку студенту):

- Дефект концов строк возвращался, потому что каждое исправление касалось только текущего файла. Одно общее правило предотвратило бы следующий случай: всё, что конвейер пишет или хэширует, — в LF, и каждая закоммиченная папка с данными получает `-text`.
- Записи PR — самое слабое доказательство в M1. CI каждый раз проходил, но в записях нет ревью, и ни один PR не сопоставляет критерии с проверками; этой записке пришлось восстанавливать это сопоставление. Если ревью проходило вне GitHub, оно не оставило следа, который мог бы увидеть руководитель практики.
- `SpecTrace-docs` отстаёт от кода. Правило "write it to `spectrace-docs`" соблюдалось, но заметка, которую написали и не отправили, невидима для всех остальных.
